# 给用户：日常命令与新仓库接入

适用版本：`codex-github-local 0.1.0`。公开仓库版整理日期：2026-09-28。

这套程序的分工是：**你在网页 Chat 确定任务，Chat 写入 GitHub，本机 Codex 执行并上传 PR，你最后决定是否合并。** 程序在你的电脑上运行；电脑休眠、关闭终端或退出 WSL 后，不能指望它继续工作。

也支持搭配原生 Codex CLI 使用：Chat 的自动任务继续交给监听程序；需要在 CLI 中边看边聊的任务，使用独立的交互目录。模型、思考强度和三种任务入口见第 9 节。

命令框每次复制一框执行。除第一条进入 Ubuntu 的命令外，本文命令均在 **Ubuntu 终端**运行。JSON 配置框要粘贴到编辑器里，不要当作终端命令执行。

## 1. 平时开始工作，只需这三步

在 Windows PowerShell 输入：

```powershell
wsl -d Ubuntu
```

进入 Ubuntu 后设置本终端路径；下面同时示范一个可选代理，请按自己的环境调整：

```bash
export PATH="$HOME/.local/bin:$PATH" http_proxy="http://127.0.0.1:7897" https_proxy="http://127.0.0.1:7897"
```

启动监听：

```bash
"$HOME/.local/bin/codex-github-local" watch
```

看到仓库名和 `idle` 就是正在等任务。保留窗口，去网页 Chat 讨论和发布任务即可。程序默认每 60 秒查看一次 GitHub；空闲查看不调用模型。新终端需要重新设置上面的环境变量，登录通常不需要重复。

不用先进入某个仓库文件夹；程序会根据登记的配置找到对应克隆。默认监听启动时已登记的所有仓库，串行处理，一个 PR 等待你决定时暂不领取其他任务。

`127.0.0.1:7897` 只是原环境使用的代理示例。无需代理时只设置 PATH，省略 http_proxy / https_proxy；需要代理时填写自己已验证的地址。

## 2. 查看状态、停止和重新启动

另开一个 Ubuntu 终端查看状态，不会打断正在执行的任务：

```bash
"$HOME/.local/bin/codex-github-local" status
```

| 看到的状态 | 含义与下一步 |
|---|---|
| `idle` | 等待新任务；没有模型调用。已结束任务会列在 history 中。 |
| `claimed` / `running` | 已领取或正在执行。保留终端，不要为了查看进度而中断它。 |
| `publishing` | 执行阶段已经结束，正在上传分支或创建 PR。若因网络退出，修好网络后重启可继续发布，不会重跑模型。 |
| `pr_open` / `waiting_review` | PR 已创建，等待你检查和决定是否合并。 |
| `blocked` | 已停止；查看 Issue 回执和本机报告，先解决原因。 |
| history 中的 `accepted` | 已核对人工合并包含原候选提交，并同步了本地主分支。 |
| history 中的 `rejected` | 任务或 PR 已关闭，现场与记录保留。 |

空闲时在监听窗口按 `Ctrl+C` 可停止；下次仍用 `watch` 命令启动。执行中按 `Ctrl+C` 会中断当前任务并留下阻塞记录，重启不会自动把它重新执行。

诊断需要先在空闲时停止监听，再运行：

```bash
"$HOME/.local/bin/codex-github-local" doctor
```

也可以只检查一次队列、处理当前步骤，然后退出，不持续监听：

```bash
"$HOME/.local/bin/codex-github-local" run-once
```

`doctor`、`run-once` 和 `watch` 共用执行锁，不要在监听运行时另外启动它们。`status` 可以同时查看。首次出现真实任务阻塞时，优先保留现场和错误报告，不要删除状态目录来“重新开始”。

## 3. 每次给网页 Chat 什么

新开一个网页 Chat 时，提供三样东西：

1. [给 Chat 的协作说明](Chat协作手册.md)全文，或上传该文件。
2. 目标 GitHub 仓库链接。
3. 本节导出的**本地配置摘要**，告诉它实际允许的路径和已登记的检查。

下面的 OWNER、REPO 和 YOUR_GITHUB_LOGIN 都是占位符，请先换成自己的仓库和账号：

```bash
repo_full='OWNER/REPO'
```

定位已生效的配置：

```bash
config_file="$HOME/.local/state/codex-github-local/repos/${repo_full//\//__}/config.json"
```

导出给 Chat 的摘要：

```bash
python3 -c 'import json,sys; c=json.load(open(sys.argv[1],encoding="utf-8")); keys=("repository","authorized_users","base_branch","allowed_roots","protected_paths","required_checks","checks","max_attempts","max_changed_files","max_file_bytes"); print(json.dumps({"bridge_version":"0.1.0",**{k:c[k] for k in keys}},ensure_ascii=False,indent=2))' "$config_file"
```

复制输出给 Chat。配置里不应放密钥；不要上传 Codex/GitHub 的认证文件、完整业务日志或真实数据库。

日常可以这样说：

> 请读取这个仓库最新 main 和项目规则，先帮我把“这里写具体需求”整理成一个小任务，说明要改什么以及如何验收，暂不发布执行评论。

确认范围后说：

> 按刚才确定的范围执行，使用本地协作协议发布一个任务。完成后给我真实 Issue 链接，最后仍由我决定合并。

收到 PR 后说：

> 请读取 Issue 和对应 PR 的最新提交、差异、检查与 handoff，核对是否满足验收，列出必须修改的问题及未验证项，给出是否建议合并的结论。

网页 Chat 不会因为 GitHub 更新就自动收到新消息；需要结果时让它主动刷新。普通聊天文字、普通 Issue 正文或评论中的“继续”不会触发本机任务，执行端只认规定格式的执行评论。

## 4. PR 出现后怎么处理

检查修改范围、候选提交、测试结果和 `tasks/GH-<Issue号>/handoff.md`。确认后在 GitHub 选择 **Create a merge commit** 合并。程序下一次检查会验证候选提交已进入 main，再同步本地并记录 `accepted`。

本版的接纳核对不支持 squash/rebase。若仓库只允许这些方式，先适配程序和流程；不要把它们当成与普通 merge commit 等价的操作，也不要为了启用程序擅自改仓库规则。

若 PR 等待期间 main 已前进，程序会暂停并提示重新比较。不要假定旧检查已经验证过合并后的整体代码。需要重做时关闭旧 PR 和旧 Issue，再用新基线发布新任务。关闭 PR 后，旧 Issue 可能仍然打开，修订前一并关闭能避免混淆。

GitHub 合并、执行端记录 `accepted`、生产部署是三件不同的事。此程序不会部署服务器。也不要用旧演示包的 `runner.py accept` 来接纳这里的 GitHub PR。

## 5. 以后接入另一个仓库

**每个新仓库登记一次。** 同一账号已有工具和登录时，不需要重装 Codex 或 GitHub CLI。下面提供的是“先跑通文档任务”的通用配置，实际代码任务还需要该项目自己的检查。

### 5.1 先确认仓库适合当前版本

等当前任务和 PR 处理结束、状态回到空闲后，停止监听。把下面的示例仓库名改成真实仓库；不要直接照抄 `my-project`：

```bash
repo_full='OWNER/REPO'
```

确认本机 GitHub 账号：

```bash
gh api user --jq .login
```

查看这个仓库的状态：

```bash
gh api "repos/$repo_full" --jq '{repository:.full_name,default_branch:.default_branch,can_push:.permissions.push,has_issues:.has_issues,allow_merge_commit:.allow_merge_commit,archived:.archived}'
```

当前版本要求：仓库有初始提交、默认分支是 `main`、当前账号能推送、Issue 已启用、仓库未归档；要完成自动接纳核对，还需能采用普通 merge commit。默认分支是 `master` 等其他名字时，需要先适配程序，不能只把配置中的 `main` 改个名字。

以上 `gh api` 是读取命令，`--jq` 只筛选返回字段。[GitHub CLI 官方说明](https://cli.github.com/manual/gh_api)

### 5.2 给新仓库准备一个配置文件

先按仓库 README 将本工具克隆到 ~/codex-tools/chat-codex_cli，再设置程序目录；若克隆在其他位置，改为实际路径：

```bash
bridge_source="$HOME/codex-tools/chat-codex_cli/codex-github-local"
```

确认安装入口仍在：

```bash
test -f "$bridge_source/setup.py" && echo '安装入口存在'
```

保留这份源程序包或它的备份 ZIP。安装到 `~/.local/share/` 的目录只包含运行组件，**不包含 setup.py**；新增仓库仍需从源程序包运行安装入口。

建立存放配置的目录：

```bash
mkdir -p "$HOME/.config/codex-github-local/profiles"
```

按仓库名生成配置文件路径：

```bash
profile_file="$HOME/.config/codex-github-local/profiles/${repo_full//\//__}.json"
```

用编辑器打开：

```bash
nano "$profile_file"
```

将下面 JSON 粘贴到编辑器，把 `repository` 改为真实的 `OWNER/REPO`，把 `authorized_users` 改为实际发布任务、运行本机程序的 GitHub 登录账号。组织名不一定是登录账号。不要保留示例仓库名。

```json
{
  "repository": "OWNER/REPO",
  "authorized_users": ["YOUR_GITHUB_LOGIN"],
  "base_branch": "main",
  "allowed_roots": ["docs/", "tasks/"],
  "codex_command": ["codex"],
  "max_attempts": 2,
  "model_timeout_seconds": 1200,
  "max_changed_files": 8,
  "max_file_bytes": 131072,
  "protected_paths": [
    "AGENTS.md", ".gitignore", ".github/", ".codex/", "automation/",
    "schemas/", "data/", "docs/START_HERE.md", "docs/STATUS.md",
    "docs/CONTROL_PLANE.md", "docs/COLLABORATION.md",
    "tasks/BOARD.md", "tasks/_template/"
  ],
  "roles": {
    "worker": {"model": null, "reasoning_effort": null},
    "reviewer": {"model": null, "reasoning_effort": null}
  },
  "required_checks": ["diff_whitespace", "task_handoff"],
  "checks": {
    "diff_whitespace": {
      "argv": ["git", "diff", "--check", "main", "HEAD"],
      "timeout_seconds": 60
    },
    "task_handoff": {
      "argv": ["{python}", "{bundle}/handoff_check.py", "{task_id}"],
      "timeout_seconds": 30
    }
  }
}
```

在 nano 中按 `Ctrl+O`、回车保存，再按 `Ctrl+X` 退出。如果没有 nano，也可以用普通文本编辑器保存为 `.json`，随后把 `profile_file` 设置为该文件的真实 Ubuntu 路径。

这份通用配置只开放 `docs/`、`tasks/`，首个任务请进一步限为具体 Markdown 文件。`diff_whitespace` 检查基线 main 到候选 HEAD 的空白格式；`task_handoff` 只检查交接记录结构。**两项通过不能证明项目功能正确。** 不要把辞书项目的 `project_handoff` 检查原样搬到没有对应脚本的其他仓库。

先检查 JSON 能读取，并确认里面的仓库名就是目标仓库：

```bash
python3 -c 'import json,sys; c=json.load(open(sys.argv[1],encoding="utf-8")); assert c["repository"]==sys.argv[2], "配置中的仓库名不一致"; print("配置可读取：",c["repository"])' "$profile_file" "$repo_full"
```

### 5.3 安装登记并自动克隆

```bash
python3 "$bridge_source/setup.py" --profile "$profile_file"
```

默认新建 `~/codex-workspaces/OWNER/REPO`。程序会检查 GitHub/Codex 登录并登记配置，不会在这一步调用模型、发布任务或推送代码。

如果默认目标目录已经存在，停下来保留它。当前安装器不直接接管任意已有克隆；可以选择另一个**尚不存在**的专用目录，例如下面的路径也要按实际情况修改：

```bash
python3 "$bridge_source/setup.py" --profile "$profile_file" --root "$HOME/codex-workspaces/my-project-codex"
```

安装成功后，按第 3 节导出新仓库的本地配置摘要，交给新网页 Chat。再重新启动监听：

```bash
"$HOME/.local/bin/codex-github-local" watch
```

监听只在启动时读取“有哪些仓库”，新增登记后必须重启。一个监听程序覆盖多个仓库时，当前同一个 GitHub 登录账号必须对所有这些仓库有权限，且在各自的 `authorized_users` 里。

让 Chat 先发布一个小的文档任务，验证领取、执行、PR 和人工合并；这能检查新仓库的真实连接。新项目没有 `AGENTS.md` 或 `docs/START_HERE.md` 等约定文件时，让 Chat 明确说明，以已有项目文档为准；不要为套用旧项目而复制一套辞书目录。

## 6. 从文档任务扩展到代码任务

网页 Chat 能编辑 GitHub，不表示它能修改本机配置。放开代码任务前，需要依据该项目实际情况增加允许目录和固定检查。

等当前任务及 PR 都处理完，停止监听；按第 3 节设置 `repo_full` 和 `config_file`。备份生效配置：

```bash
cp -- "$config_file" "$config_file.before-$(date +%Y%m%d-%H%M%S)"
```

编辑真正生效的配置：

```bash
nano "$config_file"
```

| 修改项 | 应如何决定 |
|---|---|
| `allowed_roots` | 加入真实业务目录，例如某项目的 `src/`、`tests/`，或辞书项目的 `app/`；不要凭另一个库的布局照搬。 |
| `checks` | 登记已经能在本地执行的项目检查，用参数数组填写，不是随意拼接的 shell 字符串。 |
| `required_checks` | 指定每个任务都必须执行的检查。该列表中的名字须存在于 `checks`。 |
| `protected_paths` | 保留公共规则、敏感数据和控制配置的保护；按新项目的实际结构补充。 |

检查从任务 worktree 中运行；未提交的 `.venv` 不会自动出现在每个 worktree。若依赖某个虚拟环境，应先在本机准备好，并在检查中使用其解释器的绝对路径。`{python}` 是启动调度器的 Python，不会自动选择项目环境。`{bundle}` 仅在安装登记时展开；直接编辑生效配置时，要用实际程序路径。

保存后运行 `doctor`，然后重新导出配置摘要给 Chat，再启动 `watch`。`doctor` 验证启动条件和配置格式，**不会替你跑完新增的项目测试**。

已经登记过的仓库，再运行 `setup.py --profile ...` 会保留原生效配置。只改源 profile、再运行安装命令，不能更新已登记配置。

## 7. 只选择某个仓库与查看故障

要只监听一个仓库，先确认其他仓库没有执行中或待处理的任务/PR，停止原监听，按第 3 节设置 `config_file` 后运行：

```bash
"$HOME/.local/bin/codex-github-local" --config "$config_file" watch
```

`--config` 放在子命令前。不要启动多份监听，也不要用选择仓库的方式绕过其他仓库尚未处理的状态。默认的 `watch` 已能串行管理全部登记仓库。

程序退出报错后，可以读取最新错误：

```bash
cat "$HOME/.local/state/codex-github-local/last-error.json"
```

这是最近一次失败的记录，成功重启后它也可能仍保留；结合时间和 `status` 判断，不要只凭旧错误认定程序仍然故障。

查看某个任务的本地审阅报告时，将仓库名与 Issue 号换成真实值：

```bash
repo_full='OWNER/REPO'
```

```bash
issue_number=5
```

```bash
cat "$HOME/.local/state/codex-github-local/repos/${repo_full//\//__}/runtime/outbox/GH-$issue_number/review.md"
```

这里的 `5` 只是命令示例，不表示 Issue #5 已存在或已执行。领取前就失败的任务可能还没有 outbox；此时先看 `last-error.json` 和同一 runtime 下的 `bridge.json`。

若是 `blocked`，先修正原因，再关闭旧 Issue；已有 PR 的同时处理旧 PR。随后重启，让程序登记关闭结果，再让 Chat 用新 Issue 和新基线发布修订任务。不要编辑原执行评论、删除本地状态或靠反复重启重跑同一任务。

### 登录与网络问题

Codex 登录检查：

```bash
"$HOME/.local/bin/codex" login status
```

GitHub 账号检查：

```bash
gh api user --jq .login
```

只有 GitHub 登录失效或需要重新授权时，再执行：

```bash
gh auth login --hostname github.com --git-protocol https --web
```

如果 Ubuntu 无法自动打开浏览器，就在 Windows 浏览器打开终端提示的 GitHub 授权地址并完成操作；不要把一次性代码发到聊天中。此登录方式使用浏览器授权。[GitHub CLI 官方登录说明](https://cli.github.com/manual/gh_auth_login)

出现解析域名或连接失败时，先检查 Windows 代理是否运行，并重新执行第 1 节的环境设置。网页 GitHub 连接、本机 GitHub CLI 登录、本机 Codex 登录是各自独立的条件。

## 8. 验证状态与本地目录

历史验证的来源、范围和限制见 [验证记录](VALIDATION.md)。本仓库提供源码与复现步骤，不代表你的机器或新仓库已经执行成功。原始模型日志、项目配置和业务仓库标识不公开。

本机目录速查：

| 用途 | 位置 |
|---|---|
| 已安装程序 | `~/.local/share/codex-github-local/0.1.0/` |
| 日常命令入口 | `~/.local/bin/codex-github-local` |
| 独立克隆 | `~/codex-workspaces/OWNER/REPO/` |
| 生效配置 | `~/.local/state/codex-github-local/repos/OWNER__REPO/config.json` |
| 本地任务、证据与 worktree | 上述同一仓库目录下的 `runtime/` |
| 新仓库安装入口 | 原源程序包中的 `setup.py`，不是已安装程序目录 |

程序默认最多执行两轮，即初次执行加至多一次修复；执行、修复和独立审阅会调用模型，空闲轮询不会。当前没有开机自启、自动合并或跨电脑抢占任务的功能。

## 9. 像普通 Codex 一样对话：自动与交互混合使用

**可以保留网页 Chat 派任务，同时直接使用原生 Codex CLI。** 但当前自动程序调用的是独立的 `codex exec`；它把输出保存为日志，不提供可输入消息的交互界面。另开一个 CLI 不会接管那次执行，也不会自动继承网页聊天全文。[OpenAI 非交互执行说明](https://learn.chatgpt.com/docs/non-interactive-mode)

按每个任务的需要选择入口：

| 本次想怎样做 | 让 Chat / CLI 做什么 | 是否自动领取 |
|---|---|---|
| Chat 派任务，全程自动执行 | Chat 发布 `[codex] ` Issue 和规定格式的执行评论；原监听继续工作 | 是 |
| Chat 整理任务，我在 CLI 中边看边聊 | Chat 创建 `[manual] ` Issue，写清任务；不发布 `/codex-local run` 评论。你在 CLI 中让它读取该 Issue | 否，由你在 CLI 发起 |
| 我直接在 CLI 提需求 | 在交互目录启动 Codex，直接输入需求；可让它按项目规则检查、提交任务分支并创建 PR | 不经过自动队列 |

前两种都保留 GitHub 作为任务记录。交互模式开始后，你可以继续输入补充要求；这才是能切换模型、看到操作和对话的原生 CLI。自动任务已经执行或待审阅时，不把同一个任务再交给第二个执行会话。

### 9.1 为直接对话准备一次独立克隆

原目录 `~/codex-workspaces/OWNER/REPO` 由自动程序管理。为交互工作新建一个克隆，避免手动切分支或未提交修改影响自动队列。它连接同一个 GitHub 仓库，提交到远端后仍能互相看到。

另开 Ubuntu 终端，设置路径和代理：

```bash
export PATH="$HOME/.local/bin:$PATH" http_proxy="http://127.0.0.1:7897" https_proxy="http://127.0.0.1:7897"
```

第一次创建交互目录，第二个参数指定本地位置：[GitHub CLI 克隆说明](https://cli.github.com/manual/gh_repo_clone)

```bash
gh repo clone OWNER/REPO "$HOME/codex-workspaces/OWNER/REPO-interactive"
```

如果这个目录已经存在，先确认它就是此前创建的交互克隆；不用重新克隆，也不要删除现有内容。新克隆尚未准备项目依赖，不能因为克隆成功就宣称功能测试环境已就绪。

新克隆也不会继承自动目录中的 Git 提交身份。将 YOUR_GITHUB_LOGIN 换成自己的提交名，为这一个克隆配置身份，不修改全局 Git 设置：

```bash
git -C "$HOME/codex-workspaces/OWNER/REPO-interactive" config --local user.name "YOUR_GITHUB_LOGIN"
```

使用当前已登录 GitHub 账号的 noreply 邮箱：

```bash
interactive_email="$(gh api user --jq '(.id|tostring) + "+" + .login + "@users.noreply.github.com"')" && git -C "$HOME/codex-workspaces/OWNER/REPO-interactive" config --local user.email "$interactive_email"
```

其他账号使用自己的提交名和登录信息；上述邮箱不是登录凭据。

启动原生 Codex：

```bash
cd -- "$HOME/codex-workspaces/OWNER/REPO-interactive" && "$HOME/.local/bin/codex"
```

以后只需设置本终端环境，再执行上面这条启动命令。其他仓库按同样方式给它建立自己的 `-interactive` 目录，不需要给交互克隆再运行自动程序的 `setup.py`。

### 9.2 选择模型和思考强度

进入 Codex 的输入界面后输入 `/model`，从当前账号实际可用的列表中选模型及其支持的思考强度；再用 `/status` 查看当前设置。可用模型、强度和菜单细节以本机 CLI 为准，不照抄未经确认的模型名。[OpenAI CLI 命令说明](https://learn.chatgpt.com/docs/developer-commands?surface=cli)

这些 `/` 命令输入在 **Codex 对话框**，不是普通 Ubuntu 提示符中。任务执行时可查看操作输出；对文件的修改可用 `/diff` 查看。

自动程序另有每个仓库配置中的 `roles.worker` 和 `roles.reviewer`，分别控制执行者、审阅者的 `model` 与 `reasoning_effort`。初始值 `null` 表示不通过该配置强制指定，交由 Codex 的有效配置或默认值决定；不表示没有模型，也不表示“自动选择最强模型”。用户级和项目级配置都可能参与生效。[OpenAI 配置说明](https://learn.chatgpt.com/docs/config-file/config-basic)

如果要固定自动任务使用的模型和强度，等所有当前任务/PR处理完、停止监听后，再按第 6 节编辑生效配置中的这两个角色。仅使用已在本机确认可用的模型与强度。不要以为在另一个 CLI 会话切过模型，就已经核对了自动任务的最终设置。

### 9.3 把 Chat 的任务交给交互 CLI

告诉网页 Chat：

> 这次用 CLI 交互模式。请把已确定的需求写成一个标题以 [manual] 开头的 Issue，正文写清目标、范围、验收和必要上下文，不添加 /codex-local run 执行评论。给我真实链接，我会在 Codex CLI 里执行。

随后在交互 CLI 输入下面这段，把 Issue 链接和任务范围换成真实内容：

> 请读取这个 Issue：这里粘贴实际链接。先读 AGENTS.md 和项目约定，检查当前工作区以及远端 main，在保留本地修改的前提下确定基线。按 Issue 的目标与范围工作，用独立任务分支，记录实际检查和 handoff。完成后推送该任务分支并创建 PR，交给我决定是否合并，不部署。不要改自动程序管理的克隆或 runtime；如果这个 Issue 已由自动程序领取，先告诉我，避免重复执行。

这段话包含“完成后推送分支并创建 PR”的授权；如果本次只想讨论或本地修改，应先删除这句话并说明实际范围。CLI 可使用当前 Ubuntu 中已登录的 GitHub CLI 读取私有 Issue；网页 Chat 的完整聊天需要先整理进任务正文。

直接在 CLI 提新需求时，同样写明目标、允许范围和验收。无需为了形式先回网页 Chat 创建 Issue。

### 9.4 原型分支与正式实现：弱模型探索、强模型生产化

对于前端页面、交互设计、实验界面等需要先“做出一个壳子再决定正式实现”的任务，可以在同一个 `[manual]` Issue 下分成两个阶段：

1. **prototype 阶段**：较快或较弱的交互模型与用户讨论，在独立分支中快速制作页面、交互或结构原型。
2. **production 阶段**：更强的模型从最新 `main` 重新建立正式分支，只把 prototype 当作视觉、布局、交互与需求参考，再结合真实项目架构完成生产实现。

推荐命名：

```text
prototype/GH-7-ui
feature/GH-7-final
```

关键原则是：**prototype 可以作为参考，但不要默认成为正式实现的 Git 祖先。** 正式实现应从当时最新的 `main` 分叉，而不是从 `prototype/GH-7-ui` 继续生长。这样可以保留原型带来的设计信息，同时避免把假数据、临时 CSS、简化状态、临时 API 或探索期结构直接带进生产代码。

同一个 Issue 可以记录两个阶段，不要求为 prototype 和 final 各建一个 Issue。prototype 是否推送 GitHub取决于是否需要跨机器、跨模型或长期保存参考；若只在同一台机器临时使用，也可以仅保留在本地分支/worktree。正式进入 `main` 的通常只有 final 分支对应的 PR。

如果两个模型要同时读写代码，使用不同 worktree 或独立克隆，不要让两个 Codex 会话同时修改同一个工作目录。示意：

```text
main
 ├─ prototype/GH-7-ui      # 原型，仅参考
 └─ feature/GH-7-final     # 从 main 开始的正式实现
```

例如从最新远端 main 建正式 worktree：

```bash
git fetch origin
git worktree add \
  -b feature/GH-7-final \
  ../REPO-GH-7-final \
  origin/main
```

正式模型可以读取 prototype 的差异而无需 merge：

```bash
git diff origin/main...origin/prototype/GH-7-ui
```

也可以读取 prototype 中某个文件：

```bash
git show origin/prototype/GH-7-ui:path/to/file
```

给正式模型的交接应明确说明：prototype 只定义“想做成什么样”，真实数据接入、状态管理、错误处理、接口调用和项目结构以最新 main 为准；可以复用确实合适的 UI/CSS/组件，但不要把 prototype 的工程实现默认视为正确。

### 9.5 连续复用同一 Codex 对话，但每个新 Issue 刷新代码基线

**聊天对话可以连续，Git 分支不能连续继承旧 prototype。** 例如弱模型已经在同一个 Codex 对话中完成 GH-7，之后完全可以继续用这条对话讨论 GH-8，以保留用户偏好、设计取舍和项目背景；但开始 GH-8 前，应重新读取当前仓库、同步最新 `main`，再从最新 main 创建新的 GH-8 分支。

正确关系：

```text
GH-7:
最新 main
 ├─ prototype/GH-7-ui
 └─ feature/GH-7-final -> PR -> merge

GH-8:
新的 main（已包含 GH-7 正式成果）
 ├─ prototype/GH-8-ui
 └─ feature/GH-8-final -> PR -> merge
```

不要这样做：

```text
prototype/GH-7-ui
  -> prototype/GH-8-ui
  -> prototype/GH-9-ui
```

否则新任务会继承旧 prototype 中本来不准备进入正式代码的临时实现。

开始新 Issue 时，可以在原 Codex 对话中明确要求：

> 上一个任务已经结束。现在开始新的 Issue。先不要修改；重新读取当前项目，fetch 远端并确认最新 main。不要依赖你对旧代码状态的记忆，也不要从旧 prototype 分支继续开发。基于最新 main 创建本 Issue 的新分支后，再读取新 Issue 并给出方案。

因此可以长期保留“原型/快速讨论”和“正式实现/强模型”两类 Codex 对话或工作位；**对话负责保留讨论上下文，Git 的最新 main 负责提供当前代码事实。**

### 9.4 两个入口的边界

自动入口和交互入口可以用于不同任务；两个克隆不代表远端主线互不影响。自动 PR 等待审阅时，先完成它的审阅和处理，再合并另一个任务；否则 main 前进会触发原自动程序的暂停检查。

交互任务不会自动获得协作程序的路径校验、固定检查、独立审阅或 `accepted` 记录。需按该任务实际执行的证据报告结果，不能将手动 PR 冒称为自动程序已验收。也不能把交互模式当成扩大用户授权的理由。

已经由自动程序执行并生成 PR 的任务，应保持候选与配置不变。需要重做时先处理旧任务及 PR、保留记录，再按新的执行方式创建修订任务，不在交互 CLI 中修改自动程序保存的候选。

下面用 GH-5 举例，需换成自己实际存在的任务；若只是想看自动任务的记录，可在第二个 Ubuntu 终端读取报告：

```bash
cat "$HOME/.local/state/codex-github-local/repos/OWNER__REPO/runtime/outbox/GH-5/review.md"
```

查看第一轮执行者的原始事件日志：

```bash
tail -n 30 -F "$HOME/.local/state/codex-github-local/repos/OWNER__REPO/runtime/outbox/GH-5/worker-1.stdout.log"
```

这会显示 JSON 事件并跟踪新增内容；任务已经完成时没有新的执行输出。按 `Ctrl+C` 只退出这个查看命令，不会停止另一终端中的监听。这里的日志窗口不能给执行者发消息；要边执行边对话，应为新任务选择上面的交互入口。
