# V2 指令协议与故障恢复

本文定义 [V2设计方案](V2设计方案.md) 的实施合同。所有新增字段、API 和状态均为设计要求，尚未由当前原型完整实现。业务 TaskContract 继续使用版本 2，远程投递元数据独立版本化；现有 V1 和历史 V2 授权不被隐式升级。

## 1. 远程消息的身份

V2 任务 Issue 标题以 `[codex-v2] ` 开头，唯一授权评论第一行是 `/codex-v2 run`。控制 Issue 对应 `[codex-v2-control] ` 和 `/codex-v2 control`。后面严格跟一个 JSON 代码块，不执行 Issue 正文、标签或普通评论中的自然语言。

任务和控制使用当前版本 2 信封，新增必填 `delivery` 对象。任务内容仍放在现有 `task` 字段，控制仍放在 `control` 字段；不并行发明第二份任务字段。

| delivery 字段 | 约束 |
| --- | --- |
| `schema` | 固定为 `1`，未知版本拒绝 |
| `request_id` | 发布前生成的 UUID；同一次请求重试必须复用 |
| `host_id` | 本地已登记的唯一主机 ID；不支持通配或抢占 |
| `issued_at / expires_at` | UTC 时间；默认领取窗口 24 小时，可在发布前明确调整 |
| `policy_digest` | Chat 读取的本地能力摘要哈希；任务及配置变更不一致时拒绝；status/pause/cancel 的例外见下文 |

`expires_at` 只限制尚未领取的任务，不在正在执行时偷偷中止；运行时限由冻结预算管理。主机时钟异常或发行时间明显在未来时停止领取并报告。

系统从 GitHub API 取得并保存仓库数字 ID、Issue 数字 ID 与编号、评论数字 ID、作者数字 ID、创建/更新时间及原文。信封不能自报“我是 Owner”。仓库名便于阅读，数字 ID 用于身份核对；账号改名不应静默扩大授权。

任务主键是 `(repository_id, issue_id)`，显示名可用 `OWNER/REPO#N`。`GH-N` 只在一个仓库内唯一；数据库、证据目录、API、取消命令和 PR 标识不能只用 `GH-N`。

去重键是 `(host_id, request_id)`；同键同已验证载荷返回原记录，同键不同载荷或不同任务来源拒绝。另对 `(repository_id, comment_id)` 建唯一约束。保存原文 SHA256 和规范化载荷 SHA256：前者审计原评论，后者用于语义一致性校验。

## 2. Chat 发布步骤

1. 读取最新仓库基线、适用规则、主机状态和能力摘要；状态陈旧时明确“尚未确认在线”。
2. 写清目标、非目标、read/write scope、验收、固定检查、预算、模型策略及发布方式。所有运行所需信息必须进入合同或可访问输入，不依赖聊天记忆。
3. 创建 Issue，取得真实编号，再填写 task/control ID。发布前重新读取基线并核对范围。
4. 添加唯一授权评论并回读，核对作者、正文、基线和时间。创建/评论响应结果未知时先查询已有结果，不能盲目再发。
5. 把真实链接与“已发布、等待主机领取”返回用户。主机持久化回执出现后才报告已领取。

第一次使用必须导入本地生成的能力摘要，其中包含已登记仓库/Host、策略哈希、可用检查、模型配置、允许范围及限制。摘要是配置证据，不证明主机当前在线。不得把本工具仓库自动登记为业务任务仓库。

接入前在用户实际使用的手机 Chat 中核对四项能力：读仓库、创建普通 Issue、向普通 Issue 添加评论、回读完整评论。当前桌面 GitHub 工具暴露了 Issue 创建能力，但评论工具描述偏向 PR，不能据此宣称手机端已可用。必须在不触发执行的测试 Issue 中实测作者身份与普通 Issue 评论；若手机端只有读取能力，先接入明确支持这些写动作的连接器。手工复制指令可作临时路径，但不算“Chat 自动派单”验收通过。此项验证无需给家中电脑开放端口。

修改目标、基线或范围时新建 Issue 和 request_id，关联被取代任务。编辑旧执行评论、重复授权评论、重新打开旧 Issue 都不能重启模型。授权评论被删除或改变时：领取前拒绝；运行中一旦检测到就停止新增副作用并保留现场；发布前必须重新确认。轮询存在观测延迟，不宣称编辑可即时撤回已执行动作。

## 3. 校验和控制动作

领取前要求：登记仓库和目标 Host 匹配；Issue 处于开放状态且不是 PR；作者和授权评论作者都在本地允许名单；唯一、未编辑授权；严格字段/类型/长度校验；基线可取得且符合本地基线策略；范围与检查在已登记能力内。

JSON 禁止重复键、未知字段、非有限数值和超大嵌套；时间和 SHA 格式严格校验；路径须规范化，拒绝绝对路径、`..`、危险 symlink、Git 元数据与本地凭据。标签只用于展示和查找，不能替代身份验证。

| 动作 | 语义 |
| --- | --- |
| `status` | 当前观测和更新时间；不修改模型或队列 |
| `pause` | 暂停全 Host 新任务领取，当前任务继续 |
| `resume` | 恢复领取；不会重放失败、中断或取消的任务 |
| `set-default-model` | 修改指定登记仓库的执行者/审阅者默认值；先探测，再在期望 revision 上提交；领取中的任务不变 |
| `cancel-task` | 显式指定 repository_id、task_id、run_id；只取消匹配运行，不误杀后来任务 |

主机级动作必须显式 `scope: host`；模型动作明确 `scope: repository`。允许动作和必填字段由表驱动验证。设置动作携带 `expected_revision`；探测不持锁，探测完成后事务中再次比较 revision，冲突返回 rejected。第一版不提供从 Issue 更换账号、开放目录、安装软件或修改任意配置的动作。

控制信封只允许 `version / repository / delivery / control`；任务信封只允许 `version / repository / base_sha / delivery / task`。`task` 沿用现有 TaskContract 字段。`control` 公共字段为 `id / action / scope / reason`，其中 reason 可选；id 是控制 Issue 自身的 `GH-N`。模型动作另要求 `role / model / effort / expected_revision`，resume 要求 `expected_revision`，取消另要求 `repository_id / task_id / run_id`。身份最终均与 GitHub 的实际来源以及登记表交叉验证。主机控制 Issue 所在仓库也必须在控制允许名单内。

模型探测取得同一个执行槽；已有任务运行时设置命令保持 pending，不抢占执行，不堵塞 status/pause/cancel。远程取消的 run_id 来自领取回执。未领取任务可以关闭 Issue，使其不再符合领取条件；关闭与领取交错时，以实际领取记录为准，已有运行使用明确的 cancel-task 停止。

status、pause、cancel-task 不因策略摘要过期而失效，否则配置变化可能封死停止入口；仍须通过作者、仓库、Host、期限及精确目标校验，并在回执标明使用了旧摘要。resume 和模型设置必须匹配当前策略。旧 resume 请求也不能推翻后来发生的 pause：resume 携带 expected_revision，按主机队列 revision 比较；pause 属于收紧操作，可重复应用，实际改变时递增 revision。

取消和暂停是安全控制优先级；先持久化，再由 Runner 在可中断点处理。已取消/已完成任务的重复取消返回原终态；不按模糊标题匹配进程。远程命令由 GitHub 作者认证，本地 UI 命令由本机会话认证，均进入相同命令服务；两种来源分别审计，不制造 synthetic GH-N。

## 4. 拉取和回执

使用直接仓库 REST 列表做正确性路径，不依赖全文搜索索引。GitHub Issues 列表可能含 PR，必须过滤。全量扫描分页完整处理；增量扫描使用服务端时间游标、重叠窗口和 ID 去重。只有一个扫描批次完全持久化后才前移水位；定期完整核对仍开放/活跃/待发布的任务，弥补删除、关闭和分页期间变化。

每个稳定查询键保存 ETag，遇到 304 保留已知数据；变更查询参数时不能复用旧 ETag。令牌限流预算在整个 Host 共享，串行调度远程请求，尊重 Retry-After、剩余额度与重置时间。5xx/网络错误退避加抖动；401/确定的权限失败报告配置问题，不无限重试。分页链接按 GitHub 返回值跟进，并校验目标仍是可信 GitHub API。评论 API 提供 ID、更新时间、since 和分页字段，可用于这些核对。[GitHub Issue 评论 API](https://docs.github.com/en/rest/issues/comments)

状态更新写入独立的状态评论，绝不修改执行授权评论。领取、需要处理、PR 就绪各有简明回执；过程心跳合并更新同一状态评论，不逐条上传命令输出。每条机器回执包含确定的 operation_id、来源任务标识、状态版本与内容哈希。

本地 outbox 先记录待发布内容，再发网络请求。响应丢失时，先核对远端作者、标识和完整内容，确认已有则记为已投递；不得把其他人的复制评论当成回执。外部平台不提供事务，无法绝对排除重复评论，必须可识别并收敛；重复通信绝不能再次运行任务。

主机心跳默认 5 分钟更新到一个登记时选定的状态 Issue；关键状态立即更新。超过 15 分钟没有新观测时，远端显示“状态过期，在线情况未知”，不是断言关机。状态 Issue 可以位于已登记业务仓库，不自动写到工具库。跨仓库汇总只包含该位置允许披露的信息。

用户通过 Chat 刷新进度时先读该摘要，必要时再读任务和 PR。GitHub 上发布目标、阶段、时间、检查摘要和链接；完整命令、模型日志和本地路径默认留在本机。公开仓库的任务和评论本身是公开内容，因此合同不能包含私密数据或凭据。

## 5. 持久化与状态机

SQLite 初始表按实际职责设为：`commands`、`tasks`、`attempts`、`events`、`outbox`、`runtime_settings`、`host_state`、`schema_migrations`。不为每张表新增一层服务。外部证据文件用单独清单记录相对 ID、大小、哈希、可见性和保留策略。

一次领取事务：校验命令去重 → 检查暂停/仓库占用/全局执行槽 → 记录冻结快照 → 分配 run_id/attempt_id → 写 claimed 事件 → 写回执 outbox → commit。模型调用、git 操作和 HTTP 一律在事务外。

状态保持两个维度，避免用一个 `blocked` 混淆所有情况：

| 维度 | 值及含义 |
| --- | --- |
| `phase` | queued、preflight、executing、validating、reviewing、publishing、awaiting_review、settled |
| `condition` | ready、active、waiting、needs_attention、succeeded、failed、cancelled |
| `reason` | machine-readable 原因，如 stale_base、model_unavailable、network_backoff、interrupted、input_required、cleanup_incomplete |

示例：“publishing / waiting / network_backoff”保留已经成功的执行结果；“executing / needs_attention / interrupted”保留中断现场。只有 settled 才是任务终态；needs_attention 不自动继续，也不能仅因网络恢复而转回 active。所有转换比较持久化 revision，并携带当前 run_id/attempt_id；迟到的旧进程事件只归档，不能推进新运行。

正常转换为 queued/ready → preflight/active → executing/active → validating/active → reviewing/active → publishing/active → awaiting_review/waiting → settled/succeeded。检查或审阅要求修复时，预算内从对应阶段回 executing，分配新的 attempt_id 并保留旧证据；预算耗尽进入 settled/failed。无发布任务审阅通过后直接 settled/succeeded，outcome 为 completed。模型 fallback 只允许使用冻结的候选列表并记录原因，不能在部分修改后静默切模型重跑。

任意活动阶段可停在原 phase 的 needs_attention，但必须先完成进程清理才能释放执行槽。取消先持久化 cancel_requested，不提前写 cancelled；完成清理及在途发布核对后进入 settled/cancelled。自动重试仅允许 publishing 的确定性通信操作和查询，不能从终态返回执行。用户要修改或重做任务须发布关联的新 Issue。awaiting_review 检测到未合并关闭则 settled/failed，outcome 为 rejected。

旧原型状态的迁移映射如下；有运行的状态一律先恢复核对，不直接继续。缺少可信历史阶段时 reason 使用 legacy_state_unknown，不补造成功记录。

| 旧 RunState | 新表示或恢复要求 |
| --- | --- |
| queued | queued/ready；旧授权命名空间仍需显式迁移，不能自动领取 |
| claimed、preflight | preflight/needs_attention，核对冻结和启动现场 |
| executing、validating、reviewing | 同名 phase/needs_attention/interrupted，清理并保留证据 |
| manual_review_required | validating/needs_attention，保留缺失检查和原始原因 |
| publish_ready | publishing/needs_attention；核对候选、授权和基线后才允许发布 |
| pr_open | awaiting_review/waiting；先核对真实 PR 与候选 |
| accepted | settled/succeeded，保留旧接纳证据；不足时 awaiting_review/needs_attention |
| policy_blocked、model_unavailable、execution_failed、validation_incomplete、review_rejected | settled/failed，原状态作为 reason，保留最后阶段 |
| publication_failed | publishing/needs_attention，核对是否已产生远端结果 |
| cancelled | settled/cancelled；若清理证据不足则原阶段/needs_attention/cleanup_incomplete |

`accepted` 是 settled/succeeded 的接纳结果：PR 实际合并、原候选包含于目标主线、专用本地主线安全同步。只读且不发布的任务以 completed 结案，不能伪称 PR 已合并。PR 未合并即关闭记录 rejected；不删除工作区。新设计各终态都保留 result/outcome。

启动恢复时取得全 Host 独占锁，再核对未结运行、所属进程标识和 boot/session 身份、候选、outbox。PID 本身不足以识别进程。残留执行不能可靠附着时，停止可证明属于本运行的进程组，记录清理结果，进入 interrupted。无法确认归属时报告 cleanup_incomplete，不乱杀其他 Codex。

## 6. 进程、权限与预算

监督器记录 PID/进程组、启动身份、CLI 版本、具体 argv 摘要、工作区、起止时间和退出码。使用所属 cgroup/进程组清理整个任务；先请求终止并给宽限，再强制结束，等待确认退出。清理未完成不释放执行槽。

采用固定版本 CLI 的 `exec --json`，stdout 和 stderr 分开消费，避免管道填满导致阻塞。行长、总日志量、输出缓冲和磁盘容量都有限额；达到限额不能继续无证据运行，转为需要处理并清理进程。

事件分类按精确类型和语义映射。`item.completed` 仅表示工具项结束；`turn.completed` 加上进程成功退出、最终结果可解析，才允许执行阶段结束。工具内部失败可被模型修复，不等同于整轮必然失败；`turn.failed`、非零退出、缺少可信终态或格式不兼容分别记录。未知事件保留诊断，不伪装有进展或成功。

计时分三种：进程存活、最近输出、最近实质活动；不得用自发心跳不断重置卡住检测。设计默认连续 5 分钟无输出先提示，15 分钟进入监督检查；是否停止要结合当前工具的登记超时及整任务预算。总运行预算必须独立生效，跨重启不重置，包含探测/执行/检查/审阅的已消耗时间。网络发布等待不重复消耗模型预算。

执行者以工作区写权限运行，审阅者使用独立只读上下文；无人值守不弹出无人可见的审批框，超出预设能力就停止并给出原因。`read_scope/write_scope` 是合同和发布守卫，不等于操作系统已强制执行每个读取边界；若任务要求严格隔离，必须用可验证的挂载/容器策略，否则拒绝声称符合该级别。

控制器的 GitHub 写权限不传给模型进程或测试。仅清理环境变量不足以隔离可读的 HOME、git credential helper、挂载和本地 socket；受限运行配置必须实际隐藏这些入口。Codex 认证按本地受控配置使用，浏览器和 Issue 不持有凭据。默认只接本机明确登记、用户授权的项目；执行任意外来仓库代码需要额外隔离配置。

远程任务的 network 策略是工作负载网络权限，不应误断控制器访问 GitHub 或 CLI 所需模型网络。host policy 必须说明这两种通道的隔离实现与已验证范围。白名单无法实际强制时，不以配置字段替代执行保证。

## 7. 候选与发布

执行结束先校验 diff：包括已跟踪/未跟踪文件、重命名、删除、symlink、子模块变化、文件大小、文件数、保护路径及 Git 元数据。策略越界不能以 Draft PR 绕过。

固定检查的缺失与失败分开记录。检查失败在冻结修复预算内回到执行；缺失时仅在合同明确允许且独立审阅完成后发布 Draft PR，保留未验证标记。独立审阅不能只看执行者的自述，须读取冻结合同、精确候选、差异与检查证据；只读审阅前后再次确认候选未被改动。

冻结 candidate_sha 和发布清单后，只有 Publisher 能推送 `v2/<repo-key>/GH-N/<run-id>` 候选分支。推送前检查同名分支是否指向同一 SHA，冲突则停止，不 force push。

PR 创建响应丢失时，按固定 head/base/仓库、机器标识和候选 SHA 查询已有 PR。找到一致 PR 就关联，冲突进入需要处理；不得重跑模型或者不停新建 PR。

从任务领取到发布前若基线已变化，不悄悄 rebase 并复用旧检查；记录 stale_base，保留候选，让 Chat 依据新基线准备修订。人工合并后第一版只自动核对能证明原候选祖先关系的 merge commit。squash/rebase 或同步冲突进入人工核对，不伪记 accepted。

## 8. 本地 API 与事件恢复

| 路径 | 合同 |
| --- | --- |
| `GET /api/v2/session` | 本机会话能力、Host、真实/测试模式；不泄露 token |
| `GET /api/v2/snapshot` | 同一读取事务的主机/队列/任务摘要及 `event_seq` 水位 |
| `GET /api/v2/repos/{repo_id}/tasks/{task_id}` | 任务、运行、候选和检查摘要 |
| `GET /api/v2/repos/{repo_id}/tasks/{task_id}/events?before=...` | 历史分页，稳定排序和完整性信息 |
| `GET /api/v2/events?after=...` | SSE 增量，支持 Last-Event-ID；保留窗口外返回 snapshot_required |
| `GET /api/v2/evidence/{evidence_id}` | 白名单、大小限制、脱敏、安全文本显示 |
| `POST /api/v2/controls` | request_id + typed intent；返回 202/命令 ID，并非已应用 |
| `GET /api/v2/controls/{request_id}` | 原始命令状态与实际结果，不拿最新配置冒充旧回执 |

接口中的 `{task_id}` 由服务器验证并与 repo_id 绑定。模型页仍可保留现有 `/runtime` 等兼容查询，统一从同一 Store 投影；不能保留独立 JSON writer。

查询返回记录 revision 和观察时间，写请求仅允许表列动作。HTTP 202 表示命令已持久化；命令后续状态为 pending、applied、rejected 或 needs_attention，并保留当时的结果快照。重复 request_id 同载荷返回同命令；不同载荷返回冲突。异步请求回到已切换的仓库/任务页面时，客户端按身份与 revision 丢弃过时响应。

标准事件至少包含 `schema`、单调 `seq`、`event_id`、`repository_id`、`task_id`、`run_id`、`attempt_id`、`occurred_at`、`received_at`、`type` 和经过限制的 `payload`。任务阶段、检查、命令、文件修改、公开助手说明、控制结果、发布结果分别定义类型；不把原始 CLI 任意对象直接推到 UI。

浏览器先取带水位的 snapshot，再从水位后订阅。断线保留最后数据、显示陈旧时间；恢复后按序去重和补齐，游标过期则重新取快照。刷新可还原过程；用户滚动看旧记录时不强行自动滚到底部。

前端性能目标：批量追加事件、虚拟化长历史、按需加载大输出、截断明确提示。不预先缓存所有原始日志。公开说明与可见工具活动可展示，隐藏推理不进入产品承诺。

## 9. 故障行为表

| 故障 | 处理与必须保存的证据 |
| --- | --- |
| 指令重复出现 | 返回原记录，不新增 attempt |
| 授权编辑/删除/多条 | 拒绝或停止新增副作用；记录原文/新观测摘要 |
| 领取事务后、spawn 前崩溃 | 标记启动结果待核对；不能无条件再次 spawn |
| spawn 后、PID 入库前崩溃 | 按服务/进程组归属清理并记 interrupted，不猜测未执行 |
| 执行中 GitHub 断网 | 当前已授权本地工作可继续；停止新领取，发布等待；UI 显示控制通道离线 |
| 模型认证/额度失败 | 记录 model_unavailable 或 execution_failed，不无限尝试或静默换模型 |
| 心跳正常但 CLI 无输出 | 展示最后实质活动，独立监督，不当作持续进展 |
| Ctrl+C / daemon 崩溃 / WSL 重启 | 清理所属子进程，保留现场，恢复服务但不自动重放任务 |
| 进程输出/日志超限或磁盘满 | 暂停领取、停止无法审计的执行、保留紧急诊断，不擦历史腾空间 |
| push / PR / comment 响应丢失 | 查询相同候选/operation_id，核对后完成或再试，不重跑模型 |
| 取消与发布交错 | 以已持久化阶段和远端真实结果为准；已创建 PR 保留并说明，不自动关闭或删除 |
| 一项回执长期失败 | outbox 可见且退避；允许暂停/取消，其余新工作按同步策略暂停 |
| 一仓库 await review | 锁定该仓库写任务，允许其他仓库串行前进 |
| 前端断线或模式配置错误 | 保留陈旧快照或明确错误；不回退 Mock |
| 旧库/未知 schema | 停止启动执行，保留原文件，进入显式迁移流程 |

同步策略的初始默认值：领取/需要处理/PR 就绪这类关键回执连续两个轮询周期仍未投递，则暂停新任务领取并显示原因；已授权任务可以继续，控制通道继续读取。心跳评论的单次延迟不独自阻断执行。通信恢复并清空关键积压后，仅解除系统施加的同步暂停，不覆盖用户 pause。

## 10. 数据保留与权限

关键合同、命令去重、防重放标识、候选和终态长期保留。详细日志可按本地明确策略归档，但清理不能删除防重放事实或正在使用的证据；删除操作需展示范围。数据库备份采用一致性备份，不在 WAL 写入中直接复制一个 db 文件冒充完整备份。

GitHub 评论、仓库文件和模型输出均作为外部数据处理。HTML/Markdown 展示应净化，日志中的链接不得自动执行；下载不能越过已登记证据目录。工作台没有原始 shell 输入框，远程指令不允许上传可直接执行的安装脚本。
