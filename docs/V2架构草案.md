# chat-codex_cli v2 架构草案

> 状态：设计草案 + 最小可运行核心原型。**不替换、不升级、不覆盖现有 `codex-github-local 0.1.0`。**

## 1. 为什么做 v2

现有 0.1.0 已经验证了一条很有价值的路线：

**网页 Chat 负责理解需求和发布任务 → GitHub Issue 作为授权与队列 → 本地 watcher/Codex CLI 执行 → 独立审阅 → PR → 人工 merge。**

近期真实使用暴露出几个结构性问题：

1. **读权限和写权限混在一起。** 只读安全审计需要读取全仓，但只应写报告；旧 `allowed_paths` 同时承担“可读”和“可改”，容易把任务错误地挡住，或者为了能读而放大写权限。
2. **模型可用性检查太晚。** 模型名或账号 entitlement 不匹配时，任务已经领取后才失败，浪费一次任务和额度。
3. **`blocked` 过于笼统。** 路径策略、模型不可用、执行失败、验证缺失、审阅拒绝、发布失败都落到一个词里，远程查看时很难马上判断该做什么。
4. **“验证不可用”与“实现失败”没有分开。** 例如浏览器受沙箱限制时，静态检查可能都通过，但当前实现仍被整体挡住。
5. **模型和推理强度没有任务级预算路由。** 简单文档任务和安全审计都可能烧同样昂贵的配置。
6. **任务合同缺少模板层。** audit、bugfix、UI prototype、refactor、data-check 等场景每次手写 JSON，容易出现授权范围偏差。
7. **本地证据虽然存在，但缺少统一、稳定的任务证据包结构。**

这些都不是推翻 0.1.0 的理由。相反，v2 应该保留已经证明有效的安全约束，再把权限、状态、模型、预算和证据层拆清楚。

## 2. v2 的角色模型

```text
User
  │
  ▼
ChatGPT Planner / Coordinator
  │  生成不可变任务合同
  ▼
GitHub Issue / Comment  ──────── 唯一远程授权源
  │
  ▼
Local Controller
  ├─ policy gate
  ├─ model preflight / routing
  ├─ budget
  ├─ state machine
  └─ evidence bundle
        │
        ├──────────────┐
        ▼              ▼
   Codex Executor   Codex Reviewer
        │              │
        └──── checks ───┘
               │
               ▼
          GitHub PR
               │
               ▼
          Human Merge
```

原则：

- ChatGPT 可以规划、派单、复核，但不能绕过 GitHub 任务合同直接扩大本地权限。
- Local Controller 尽量“少思考”：它负责确定性策略、状态、预算、快照和发布。
- Executor 与 Reviewer 使用不同上下文；Reviewer 默认只读。
- 人工合并继续保留，不自动部署。
- Issue 执行评论保持不可变；修订仍用新 Issue。

## 3. v2 任务合同的关键变化

### 3.1 读写权限分离

```json
{
  "read_scope": ["**"],
  "write_scope": [
    "docs/SECURITY_REVIEW.md",
    "tasks/GH-42/"
  ]
}
```

含义：

- Executor 可以读取整个仓库分析。
- 只有 `write_scope` 能产生候选 diff。
- 本机仍有更外层的 host policy；任务只能缩小权限，不能扩大本机登记权限。
- `protected_paths` 永远优先于任务写权限。

### 3.2 任务类型模板

初期定义：

- `audit-readonly`
- `code-change`
- `bugfix`
- `ui-prototype`
- `refactor`
- `data-check`
- `documentation`

模板只提供默认值，最终执行仍冻结成完整 JSON；不要让“模板名称”变成隐式授权。

### 3.3 模型策略与 preflight

```json
{
  "model_policy": {
    "executor": {
      "primary": {"name": "auto", "effort": "medium"},
      "fallbacks": [{"name": "stable", "effort": "medium"}]
    },
    "reviewer": {
      "primary": {"name": "auto", "effort": "high"},
      "fallbacks": [{"name": "stable", "effort": "high"}]
    }
  }
}
```

Controller 在创建 worktree/消耗主要额度前做最小 preflight。具体模型 ID 属于本机能力，不写死在公开模板里。

### 3.4 预算

```json
{
  "budget": {
    "max_rounds": 2,
    "max_minutes": 45,
    "review_rounds": 1
  }
}
```

预算由 Controller 执行，不依赖模型“自觉停止”。

## 4. 更细的状态机

正常路径：

```text
queued
→ claimed
→ preflight
→ executing
→ validating
→ reviewing
→ publish_ready
→ pr_open
→ accepted
```

明确区分异常：

```text
policy_blocked
model_unavailable
execution_failed
validation_incomplete
manual_review_required
review_rejected
publication_failed
cancelled
```

`manual_review_required` 不一定是失败。例如浏览器在受限环境不可运行，但代码、静态检查、独立审阅都通过时，可以根据任务策略创建 **Draft PR**，把缺失验证清楚写出来，而不是把整个实现判成不存在。

## 5. 证据包

建议每个任务本地固定：

```text
runtime/jobs/GH-N/
  task.json
  config.snapshot.json
  policy.snapshot.json
  model-preflight.json
  executor-1.jsonl
  reviewer-1.jsonl
  checks-1.json
  events.jsonl
  summary.md
```

GitHub 只上传适合长期留存的 handoff/摘要；原始日志、账号信息、本机路径、真实配置继续只保留本地。

## 6. 与 0.1.0 的关系

本轮新增的 `codex-github-local-v2/` 是**旁路原型**：

- 不修改 `codex-github-local/`。
- 不修改 0.1.0 的安装器。
- 不修改现有 profile、watcher 或运行状态。
- 不声明已经可以替换真实 watcher。

迁移建议：

1. **Phase A：纯模型/策略核心。** 先稳定合同、read/write scope、状态机、模型路由、预算。
2. **Phase B：Git/Codex adapter。** 复用已经验证过的 worktree、候选一致性和 reviewer 隔离思想，但重新写 adapter 边界。
3. **Phase C：GitHub adapter。** 兼容现有不可变执行评论，同时定义 v2 协议号。
4. **Phase D：shadow mode。** 同一 Issue 只由 0.1.0 真执行，v2 只解析/评估，不写 GitHub。
5. **Phase E：单仓灰度。** 明确切换一个测试仓库后再谈升级。

## 7. 借鉴方向

可以继续研究这些公开项目的**设计思想**，不直接复制其实现：

- repo-harness：Planner 与 Executor 的权限边界。
- repository-agent-orchestrator：Issue/PR 状态驱动、worktree、agent 生命周期。
- Claude-Codex-Orchestrator：`codex exec --json` 事件流、超时和 stall detection。
- cli-agent-orchestrator：多 session / 多 worker 管理。

我们自己的强项继续保留：不可变执行评论、配置快照、候选 SHA 一致性、人类 merge gate、blocked 不自动重放、任务 handoff。

## 8. 当前原型已经包含什么

`codex-github-local-v2/` 目前已经实现：

- v2 任务合同解析与校验；
- read/write scope 和 protected path 策略；
- 显式状态机与 validation unavailable → manual review / Draft PR 语义；
- 模型路由、Codex exec 参数构造和最小模型 preflight wrapper；
- GitHub Control Issue 解析、authorized user / immutable comment / Issue ID / repository 校验；
- gh CLI 的控制 Issue 查询、评论读取与回执发布 adapter；
- runtime settings 原子持久化与 control replay ledger；
- runtime-default → claimed task 的冻结解析；
- 本地 evidence bundle 的原子 JSON / append-only JSONL 基础设施；
- 可运行的 remote control watcher 入口；
- GitHub Actions 中的纯逻辑与 mock adapter 单元测试。

**仍未实现完整普通代码任务链**：GitWorkspace 创建/范围守卫/候选提交已有独立实现和测试，尚未与 [codex] task v2 watcher、完整 Executor/Reviewer 进程监督、stall detection、push/PR、merge 后 accepted 同步接通。现役 0.1.0 不受影响。


## 9. GitHub Control Issue：远程改变本地 Codex 状态

v2 需要第二条控制通道：除了发布代码任务，还能通过 GitHub Issue 改变本地 controller/Codex 的默认状态。

控制 Issue 使用单独前缀 [codex-control]，授权评论第一行为 /codex-local control。第一版只允许白名单动作：

- set-default-model：改变 executor/reviewer 后续任务的默认模型和思考强度；
- pause：停止领取新任务，不杀正在运行的任务；
- resume：恢复领取；
- status：向 GitHub 回写脱敏运行状态。

控制动作由 Local Controller 确定性执行并写审计记录。pause/resume/status 不调用 Codex；set-default-model 调用 read-only 最小 model preflight，成功后才更新默认值。控制动作不创建代码任务 worktree，也不产生产品 diff。

最重要的冻结规则：已经 claimed 的任务继续使用领取时的 model/config snapshot。GitHub 上新发的模型切换只影响之后领取的任务。这样 PR 的执行证据仍然可复现，不会出现中途热切模型。

当前原型已经把这条链写到 adapter 层：gh CLI 读取控制 Issue → 严格校验 → Codex 最小 model preflight → 原子更新 runtime settings → ledger 防重放/持久回执 → GitHub 脱敏回执。模型探测失败时保持上一份已知可用设置；回执发送失败只恢复投递。0.0.2 ledger schema 2 的升级边界见 v2 README。

任务合同可把模型名写成 runtime-default；任务被 claimed 时会把当时的 executor/reviewer 默认模型与思考强度冻结进 resolved task 和 evidence snapshot。因此之后新的控制 Issue 不会改变已经运行中的任务。

这条控制链目前只在 GitHub Actions 中用 mock GitHub/Codex 做自动测试，尚未在用户台式机上做真实端到端现场验证。

详细协议和示例见 codex-github-local-v2/docs/CONTROL_ISSUES.md。


## 10. 简化约束

v2 不以“功能越多越好”为目标。原 PR #2 已把源码模块从 22 个收敛到 16 个，同时保留 48 项回归。integration 只增加独立供应商 I/O 契约 `model_adapter.py`，将 ProbeResult 收到该边界；不恢复已删除的小模块。维护入口见 [INTEGRATION.md](INTEGRATION.md)。

后续新增能力遵守这些约束：

- GitHub task/control 共用一套不可变 Issue 协议，不再复制解析、作者、Issue ID、repository 校验。
- control action 使用 parser/handler 表分派；processor 只负责流水线，不堆 action-specific if/elif。
- Codex 命令构造与 model preflight 共用一个 adapter，不建立平行实现。
- runtime-default 的解析与 claim 快照放在同一处，不再拆出只有一个函数的模块。
- 新增模块前先确认它有独立生命周期或 I/O 边界；纯转发的一函数模块优先合并。
- 不为“未来可能需要”提前建立抽象层。只有第二个真实实现出现时再抽象公共接口。
- 每次重构必须由现有 GitHub Actions 回归兜底；失败先修测试，不通过删除验证来换绿色。

当前删掉了 codex_probe、control_ledger、control_processor、github_control、github_task、runtime_settings、resolution 七个重复/过细模块，分别并入 codex_adapter、control、github_protocol 和 claim。
